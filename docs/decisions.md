# Journal des décisions techniques

Les décisions métier et produit (D-01 à D-38) sont dans `dossier-projet.md`, qui fait foi.
Ce journal reçoit les décisions **techniques** prises pendant le développement : une ligne par décision, la plus récente en bas.

| Date | Décision | Raison | Options écartées |
|---|---|---|---|
| 2026-10-20 | Next.js 16.4 avec les réglages par défaut de `create-next-app` : Cache Components et Partial Prefetching activés. Les données dynamiques (créneaux, planning, session) se lisent derrière `<Suspense>`. | La vitrine est servie en coque statique rapide (principe « site premium = site rapide ») ; les deux options deviendront le défaut de la prochaine version majeure. | Désactiver `cacheComponents` : modèle de cache connu, mais dette de migration à terme. À rouvrir si la contrainte freine les lots 2 à 4. |
| 2026-10-20 | pnpm, TypeScript strict, ESLint (config Next), Prettier. `engines.node >= 24`. | Node 24 et pnpm sont déjà installés ; Prettier évite les débats de style dans les revues. | npm (plus lent, lockfile moins strict). |
| 2026-10-20 | Drizzle ORM + `postgres` (postgres-js), `prepare: false`, migrations SQL dans `drizzle/`, appliquées par `drizzle-kit migrate`. Le client n'est importable que côté serveur (`server-only`). | La contrainte d'exclusion (R-23) s'écrit en SQL pur, ce que Drizzle gère par des migrations personnalisées ; `prepare: false` est requis par le pooler Supabase ; léger en serverless. | Prisma : moteur plus lourd, migrations SQL personnalisées moins directes. |
| 2026-10-20 | Variables d'environnement validées par zod, lues à la demande (`serverEnv()`), toutes réservées au serveur : aucune `NEXT_PUBLIC_` pour la base ou Supabase. | Principe 5 : aucun accès à la base depuis le navigateur ; une page statique se construit sans secrets. | Validation à l'import : casserait le build des pages statiques. |
| 2026-10-20 | Dépendances ajoutées au lot 0 : `zod` (validation des entrées et de l'environnement), `drizzle-orm`/`drizzle-kit`/`postgres` (accès aux données), `@supabase/ssr`/`@supabase/supabase-js` (authentification côté serveur), `server-only` (interdit l'import côté client), `vitest`, `@playwright/test`, `prettier`, `dotenv` (lecture de `.env.local` par drizzle-kit et les tests). | Chacune est prévue par la transmission ou nécessaire à un principe d'architecture. Luxon, React Email, GSAP, Serwist viendront avec les lots qui les utilisent. | — |
| 2026-10-20 | Base locale sans Docker : vrais binaires Postgres 17 du paquet `embedded-postgres` (version 17.10.0-beta.17, fixée), pilotés par `scripts/db-local.mjs` (`pnpm db:start`, `db:stop`, `db:status`, `db:reset`), données dans `.local-db/`. Les tests d'intégration démarrent leur propre instance temporaire (`tests/integration/global-setup.ts`) ; en intégration continue ils utilisent le service Postgres 17 désigné par `TEST_DATABASE_URL`. | Docker Desktop ne fonctionne pas sur le poste de Florent (pas de virtualisation). Essai concluant : la contrainte d'exclusion de R-23 refuse bien un chevauchement (erreur 23P01) sur ce Postgres. Version 17 pour rester proche de la production (à confirmer à la création du projet Supabase). | Docker (impossible) ; PGlite (Postgres WebAssembly, moins fidèle) ; installation native de Postgres (démarche plus lourde pour l'utilisateur). Pile Supabase complète en local : impossible sans Docker, l'authentification se testera sur le projet Supabase de test. |
| 2026-10-20 | Tests : Vitest en deux projets (`unit` dans `src/**/*.test.ts`, `integration` dans `tests/integration` sur Postgres réel, fichiers en série) ; Playwright en deux profils, mobile 390×844 et tablette 1194×834 (WebKit), sur le build de production. | CLAUDE.md exige une vérification mobile et tablette ; la contrainte R-23 ne se teste que sur un vrai Postgres. | Tests d'intégration contre des mocks : ne prouverait pas R-23. |
| 2026-10-20 | Intégration continue GitHub Actions : lint, typecheck, migrations, Vitest, Playwright à chaque push, avec un service Postgres 17. | « Les tests tournent à chaque modification » (critère du lot 0). | — |
| 2026-10-20 | Référencement coupé tant que `ALLOW_INDEXING` n'est pas `true` (balise robots noindex). | Le site de test ne doit pas être indexé avant le lancement. | — |
| 2026-10-20 | Logo servi tel quel (`unoptimized`), non retouché, avec son bloc de métadonnées C2PA d'origine. | Fichier officiel (D-33) ; le SVG est déjà vectoriel. Le bloc de métadonnées pèse environ 16 Ko : à retirer si la page d'accueil se révèle trop lourde au lot 6. | — |
| 2026-10-20 | R-64 (email d'invitation à un avis) envoyé seulement si `NEXT_PUBLIC_REVIEWS=true`. Décision de Florent, qui m'a laissé trancher. | D-38 masque les avis jusqu'à leur lancement : inviter à laisser un avis sans page pour le publier serait incohérent. R-64 sera testée drapeau actif et drapeau coupé. | Envoyer l'email dès la V1. |

| 2026-10-20 | Variables d'environnement séparées en deux groupes (`databaseEnv()`, `supabaseEnv()`). | Une fonction qui n'utilise que la base, comme la sonde `/api/health`, n'exige pas les clés Supabase. | Un seul groupe : oblige à tout configurer pour démarrer. || 2026-10-20 | `DATABASE_URL` en local ; sur Vercel, repli sur `POSTGRES_URL` (fourni par l’intégration Supabase).
